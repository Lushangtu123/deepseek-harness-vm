# SSH 并发连接与 PentAGI 验收

2026-10-31（America/Los_Angeles），日常 VM 的受管 SSH 控制器已更新。配置、宿主权限和网络隔离没有扩大。当前结果见[结构化验收](ssh-pentagi-verification.json)。

## SSH 故障定位与处理

第一组固定只读探针：8次串行全成功，24次三路并发中4次失败。带VM包头记录的第二组：8次串行全成功，24次并发中3次失败，均在认证前；VM未发出重置包，观察到转发侧发向VM的重置。另一次同样三路并发的SSH标识读取，VM内回环36/36成功，经既有宿主转发18/36成功。服务日志没有对应的MaxStartups拒绝记录。

这些证据把本次受控复现定位到并发握手下的宿主转发通路。没有确定QEMU/libslirp内部具体源码缺陷，也不能证明所有历史未留原始证据的失败都属于同一原因。

受管调用现在共用一个跨进程私有通道，保持原主机密钥验证。排队与执行共用原来的总期限，不自动重放原命令。排队到期明确记录 `queue-timeout` / `request not sent`；发出后的SSH超时继续标为远端结果未确认。长SSH操作可能让其他读取达到自身排队期限，须等待后重新读取；VM内通过HTTP运行的任务不持有此宿主锁。

校时的读取起点和设置时间戳在取得通道后生成，避免把排队时间计入时差。默认主线程收到SIGTERM时，先让本地SSH子进程清理完毕，再释放锁；不承诺SIGKILL或宿主崩溃时同样清理，也不由本地进程结束推断远端命令未执行。实现采用[Python文件锁](https://docs.python.org/3.13/library/fcntl.html#fcntl.flock)和[单调时钟](https://docs.python.org/3.13/library/time.html#time.monotonic)。

部署后8组、每组3个独立进程的真实只读SSH请求24/24成功，每条仅提交一次。该验证覆盖受管控制器；手动直接运行SSH会绕过通道，底层转发问题仍可能触发。没有提高MaxStartups、放宽SSH策略或开放VM网络。

## PentAGI 模型到产物

在原日常VM用现有本地配置新建一次合成任务，真实deepseek-v4-pro模型调用一次worker终端，生成含随机运行标识、17+25结果与SHA-256的JSON文件。验收器直接读取worker文件，独立核对内容、127字节长度和文件摘要；模型的成功报告不作为唯一证据。随后自然任务报告成功，再显式finish自有flow，API确认finished且没有运行中的该worker，旧flow状态不变。全程约78秒，没有提交真实项目扫描。

任务观察期限300秒，创建请求只发一次，响应丢失不重新POST。只使用VM内合成目录；模型API沿用既有授权配置。此结果证明本机这一条完整链路，不能证明所有工具或未来新装账号均已可用。上次空白环境安装只验证本地API的历史结论保留。
